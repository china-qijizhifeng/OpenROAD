# GPL SoA 剩余问题与 profile 计划

分析对象：合入 fork master 的 `8bc1c3e674`。构建与差分结果见
[master 整合记录](SOA_MASTER_INTEGRATION.md)。以下区分已测事实、静态判断和待测假设，
不把旧基线的采样比例当作当前 master 的结果。

## 2026-11-06 E2B profile 结论

本轮通过 HK SWEEnvMaker 0820 的实际模板 API 选择
`flasheda-r5-cpu8-t16-20261030`，每设计一个独立沙箱并行；沙箱内原版/候选串行。
实际资源为 8 逻辑 CPU、4 物理核、16 GiB，GPL 使用有效的 1/4 线程，OpenSTA 固定 1。
没有修改程序绕过核数限制。所有数据与 Northjob 的 1/8 线程分开。

三设计 × 原版/候选 × 1/4 线程的 12 次阶段计时/OMPT 均完成，完整状态、QoR
及迭代轨迹与已验收正式版本一致。AES 与 large02 另用未插桩正式 ELF 做
`perf stat` 和独立 `perf record`，共 8 次，也全部精确一致。四份 cycles:u
99 Hz / DWARF 8 KiB 栈采样均零丢样，GPL 符号与调用链可见。
每种配置仅一次，不是三次中位数性能实验。

### 优先级应从“继续优化密度”转向线长 gather 和初始布局

下表是候选 4 线程的阶段墙钟秒；初始布局和时序反馈为 inclusive，线长 gather
为其独立子阶段。它们没有相互包含，但不能再把其中的子阶段重复加总。
阶段 root 不含输入加载和状态导出，不能与进程 wall 混为一列。

| 设计 | 阶段 root | 初始布局 | 线长 gather | 时序执行 |
|---|---:|---:|---:|---:|
| AES | 28.113 | 1.418（5.0%） | 2.589（9.2%） | 9.780（34.8%） |
| large01 | 64.321 | 27.899（43.4%） | 14.988（23.3%） | 未启用 |
| large02 | 72.208 | 30.737（42.6%） | 19.097（26.4%） | 未启用 |

large01 的初始布局中，稀疏求解 16.277 秒、矩阵构建 5.289 秒；large02 分别为
16.050 / 6.910 秒。因此初始布局直接读列值得做，但无法仅靠删 getter 省掉全部
28–31 秒；求解器是更大的组成部分。候选 4 线程初始布局也比原版多约 2.9–3.7 秒，
需要保留矩阵/RHS 逐字节对照来评估列式访问改写，不改 Eigen 的算术顺序。

large02 的未插桩 cycles 采样进一步显示：`pinGradientColumns` self 24.88%，
线长 bulk gather 的用户并行函数 7.37%；Eigen 稀疏乘法 11.64%、BiCGSTAB
相关赋值 3.99%，WA force 8.84%。这些百分比是该次全线程用户 CPU cycles
采样占比，不是阶段墙钟占比。它们支持先处理线长 gather 的实际读取与运算，
再处理初始布局；不是把 OMPT 的所有等待直接当成可删除的 OpenMP 开销。

保持逐位一致的候选方向：先量化每 pin 重复读取的 net 不变量，尝试按 net 计算
完全相同的中间式、或用连续 per-pin 梯度列供 cell 按原 pin 顺序求和。
后者会增加写入与常驻内存，必须先做独立 replay 和端到端对照；不能用倒数乘法
替代原除法、重排单 cell 求和，或先改公式再用最终 QoR 接受差异。

### OpenMP 存在开销，但累计等待不能作为耗时预算

候选 AES 4 线程的并行区计数从原版 25,413 增至 37,978；large01 从 15,548
增至 20,745，large02 从 15,025 增至 19,862。小循环的 fork/join 与更多边界
值得检查，优先考虑同一 kernel 内复用线程组，不急于添加更多细粒度并行区。

OMPT 在 4 线程真实生效，invalid pairs 为 0。单线程 runtime 没有发 wait 回调，
标为“未测得”，不是测得零。累计等待为所有线程的 thread-time，包含其他线程
在串行 STA/修复期间停驻：AES 时序阶段约 9.78 秒墙钟对应约 29.43 秒 worker
等待，不能相减得到可节省时间。large02 采样的 >0.1% self 条目也未出现
OpenMP runtime 符号；这不证明其开销为零，只说明不能把它认定为头号 CPU 热点。

### SoA 的空间代价需要进入下一轮验收

`/usr/bin/time` 的正式 ELF / `perf stat` 样本显示：AES 峰值 RSS 从
545.1 MB 增至 577.7 MB（约 +6.0%）；large02 从 1,194.9 MB 增至
1,498.2 MB（约 +25.4%），独立 record 运行也出现相近差异。
这是真实观测到的空间代价，不能继续声称列存天然省内存。尚无分配栈证据能将
全部差异归到某个结构，后续要区分常驻数值列、对象 handle、双向 CSR、WA 映射、
线程私有密度网格和构建过程临时峰值。

### 计数器支持局部性收益，但不能一概而论

E2B 的软件/硬件事件实际可用，各 stat 事件 percent-running 为 100%。
AES 的 cache-misses 从 3.273B 降至 0.623B；large02 反而从 5.212B 升至
5.772B，同时 cycles 从 977.7B 降至 733.2B。不能把两者统一解释成“缓存问题已解决”，
也不能仅凭 miss 计数判定带宽饱和。候选 branch-misses 读数为 0，保留原始读数，
不据此推断分支预测收益；客体 PMU 的这些观测不用于跨宿主机比较。

下一轮建议先做线长 gather 的局部 replay 与内存核算，再做初始布局行号视图，
同时保持真实差分；AES 的时序反馈需单独研究 repair/STA 占比，不能把减少修复次数
混入逐位一致优化。数据表见 [阶段总表](soa-e2b-profile/phase-runs.csv)、
[阶段细表](soa-e2b-profile/phase-detail.csv)、[进程资源](soa-e2b-profile/perf-runs.csv)、
[事件计数](soa-e2b-profile/perf-events.csv)和[CPU 符号](soa-e2b-profile/perf-symbols.csv)。

## profile 前的问题与证据边界

原基线下的整版 CPU 回退已修复：七配置的 84 个最终记录精确一致，
1/8 线程中位耗时分别减少 11.9%–32.6% / 33.6%–50.5%。但仍有三个待解决的问题：

1. 新 master 改了矩形 FFT 的比例、时序修复过滤和依赖接口，必须独立验证整合结果；现已完成。
2. 本轮之前的阶段采样来自 v2 的 AES，缺少 v3 高利用率设计的热点分布；现由上节补齐。
3. 局部内核已明显加速，剩余时间越来越受时序反馈、初始布局和确定性串行归约限制。

## 代码中仍然存在的工作

### 初始布局仍经对象访问列

`InitialPlace::updatePinInfo` / `createSparseMatrix`、`Instance::setCenterLocation`
及 pin 更新仍使用对象 getter。可以在一次初始求解的拓扑边界建立行号映射，
直接读实时坐标列；这是高利用率设计的候选优化。

必须保留 min/max 同坐标时的首个命中规则、movable IO 过滤、原 fanout 权重分母、
triplet 插入顺序和 RHS 累加顺序。Eigen 的求解、对齐和 ISA 不随之改变。
旧诊断中的“大设计初始布局多约 4–5 秒”是整改前测量，当前可回收时间需重测。

### WA force 连续写入后，gather 仍是跨 net 读取

force 已按 net CSR 连续写入；cell gather 要沿 cell→pin、pin→net、pin→WA 行
读取多个 net/pin 列。两种遍历的局部性目标不同，消除写侧散布不代表读侧已连续。
当前静态分配按 cell/net 数量分工，也没有按 pin 工作量均衡。

“缓存失效”“带宽受限”“高 fanout 导致负载不均”都是待测假设，不能仅凭源码确认。
先看 force/gather 的独立耗时、各线程工作和等待，再决定是否按工作量分块或进一步融合。
跨 net 的任务顺序可调整；单 net 或单 cell 内的浮点累加顺序必须保留。

### 确定性归约留下串行下限

`updateGradients` 仍按 optimizer 顺序串行累计梯度总量；`getDistance` 并行求平方后，
按原 x/y 交错顺序串行求和。它们保留逐位一致，是有意保留的约束。
普通 OpenMP reduction 或树归约会改变运算顺序，不能当作无行为变化的替换。
应先量化串行段占比，再考虑少写临时列、减少额外遍历等保持原顺序的改动。

### 派生状态的生命周期仍需明确

kind/locked、optimizer 行号映射和两套 CSR 都依赖拓扑边界。当前已集中 optimizer
增删/改绑，并有 `checkConsistency`，锁在上层解锁边界刷新。后续新增回调必须走这些入口。

另一个静态接口问题是 `GPin` 的隐式复制：通用 `SoaRow` 复制会分配新几何行，
同时按值复制 `waSlot`；而 WA 值现在由另一个行号寻址，复制后的两个对象可指向同一
WA 槽。因此通用“独立值复制”的说明不能直接套用到 GPin。现有构造、扩容及
swap-remove 路径使用移动，尚未观测到实际复制导致的运行错误；需要显式确定
GPin 是否禁止复制，或为复制定义拓扑边界和独立 WA 状态。这不是已复现的布局故障。

## 本次 profile 的协议

- 选择 AES、large01、large02，固定整合候选及同工具链 master 对照；E2B 实际物理核数使本轮采用 1/4 线程。
- 先过功能差分，再单独 profile。正式计时不带采样器，采样运行也核对完整状态与迭代数。
- 记录 initial、timing、routability、WA force/gather、density、FFT、坐标及归约的时间。
- 区分主线程墙钟、全线程 CPU 和临时阶段计时；没有计数器证据就不声称缓存或带宽原因。
- 优先检查 perf 权限。若不可用，采用经过安全性核对的本地栈采样或临时阶段计时；
  不直接复用曾在启动时崩溃的 `backtrace()` 信号处理器。
- 保留采样开销、源码/工具/二进制/输入 SHA、线程设置、符号化过程和可用的进程内存峰值。

执行顺序是：完成 master 整合验证，再根据新 profile 排初始布局、WA gather 与
时序反馈的优先级。减少 routability 回退、timing repair 次数或改变停止规则会影响 QoR，
需要独立协议，不能混入逐位一致的实现优化。
