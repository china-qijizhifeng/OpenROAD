# GPL SoA 剩余问题与 profile 计划

分析对象：合入 fork master 的 `8bc1c3e674`。构建与差分进展见
[master 整合记录](SOA_MASTER_INTEGRATION.md)。以下区分已测事实、静态判断和待测假设，
不把旧基线的采样比例当作当前 master 的结果。

## 当前结论

原基线下的整版 CPU 回退已修复：七配置的 84 个最终记录精确一致，
1/8 线程中位耗时分别减少 11.9%–32.6% / 33.6%–50.5%。但仍有三个待解决的问题：

1. 新 master 改了矩形 FFT 的比例、时序修复过滤和依赖接口，需独立验证整合结果。
2. 最后的阶段采样来自 v2 的 AES，缺少 v3 高利用率设计的热点分布。
3. 局部内核已明显加速，剩余时间越来越受时序反馈、初始布局和确定性串行归约限制。

## 代码中仍然存在的工作

### 初始布局仍经对象访问列

`InitialPlace::updatePinInfo` / `createSparseMatrix`、`Instance::setCenterLocation`
及 pin 更新仍使用对象 getter。可以在一次初始求解的拓扑边界建立行号映射，
直接读实时坐标列；这是高利用率设计的候选优化。

必须保留 min/max 同坐标时的首个命中规则、movable IO 过滤、原 fanout 权重分母、
triplet 插入顺序和 RHS 累加顺序。Eigen 的求解、对齐和 ISA 不随之改变。
旧诊断中的“大设计初始布局多约 4–5 秒”是整改前测量，当前可回收时间需重测。

### WA force 连续写入后，gather 仍是跨 net 读取

force 已按 net CSR 连续写入；cell gather 要沿 cell→pin、pin→net、pin→WA 行
读取多个 net/pin 列。两种遍历的局部性目标不同，消除写侧散布不代表读侧已连续。
当前静态分配按 cell/net 数量分工，也没有按 pin 工作量均衡。

“缓存失效”“带宽受限”“高 fanout 导致负载不均”都是待测假设，不能仅凭源码确认。
先看 force/gather 的独立耗时、各线程工作和等待，再决定是否按工作量分块或进一步融合。
跨 net 的任务顺序可调整；单 net 或单 cell 内的浮点累加顺序必须保留。

### 确定性归约留下串行下限

`updateGradients` 仍按 optimizer 顺序串行累计梯度总量；`getDistance` 并行求平方后，
按原 x/y 交错顺序串行求和。它们保留逐位一致，是有意保留的约束。
普通 OpenMP reduction 或树归约会改变运算顺序，不能当作无行为变化的替换。
应先量化串行段占比，再考虑少写临时列、减少额外遍历等保持原顺序的改动。

### 派生状态的生命周期仍需明确

kind/locked、optimizer 行号映射和两套 CSR 都依赖拓扑边界。当前已集中 optimizer
增删/改绑，并有 `checkConsistency`，锁在上层解锁边界刷新。后续新增回调必须走这些入口。

另一个静态接口问题是 `GPin` 的隐式复制：通用 `SoaRow` 复制会分配新几何行，
同时按值复制 `waSlot`；而 WA 值现在由另一个行号寻址，复制后的两个对象可指向同一
WA 槽。因此通用“独立值复制”的说明不能直接套用到 GPin。现有构造、扩容及
swap-remove 路径使用移动，尚未观测到实际复制导致的运行错误；需要显式确定
GPin 是否禁止复制，或为复制定义拓扑边界和独立 WA 状态。这不是已复现的布局故障。

## 本次 profile 应回答的问题

- 选择 AES、large01、large02，保留 1/8 线程；固定整合候选及同工具链 master 对照。
- 先过功能差分，再单独 profile。正式计时不带采样器，采样运行也核对完整状态与迭代数。
- 记录 initial、timing、routability、WA force/gather、density、FFT、坐标及归约的时间。
- 区分主线程墙钟、全线程 CPU 和临时阶段计时；没有计数器证据就不声称缓存或带宽原因。
- 优先检查 perf 权限。若不可用，采用经过安全性核对的本地栈采样或临时阶段计时；
  不直接复用曾在启动时崩溃的 `backtrace()` 信号处理器。
- 保留采样开销、源码/工具/二进制/输入 SHA、线程设置、符号化过程和可用的进程内存峰值。

预期顺序是：完成 master 整合验证，再根据新 profile 排初始布局、WA gather 与
时序反馈的优先级。减少 routability 回退、timing repair 次数或改变停止规则会影响 QoR，
需要独立协议，不能混入逐位一致的实现优化。
